# 초보자용 설명 주석 달기

사용자가 지정한 코드 파일에 **초보자가 읽고 이해할 수 있는 한국어 주석**을 원본 파일에 직접 추가한다.
산출물은 "주석이 추가된 원본 코드 파일" 그 자체다. 별도 문서를 만들지 않는다.

가장 중요한 원칙: **코드의 동작은 절대 바뀌면 안 된다.** 주석만 추가한다. 들여쓰기, 공백, 변수명, 줄 순서, 기존 주석 모두 그대로 둔다. 초보자를 돕겠다고 코드를 "정리"하거나 버그를 고치는 순간, 사용자는 자기 코드를 더 이상 믿을 수 없게 된다. 버그나 개선점이 보이면 코드는 건드리지 말고 마지막 채팅 요약에서 따로 알려준다.

## 작업 순서

### 1. 대상 파일 정하기
- 사용자가 파일 경로, 여러 파일, 또는 폴더를 지정한다.
- 폴더라면 그 안의 소스 코드 파일만 대상으로 한다. `node_modules`, `.git`, `venv`, `dist`, `build`, 자동 생성 파일(`*.min.js`, lock 파일 등), 바이너리는 제외한다.
- 폴더 안 대상 파일이 10개를 넘으면 목록을 보여주고 전부 할지 사용자에게 먼저 확인한다 (작업량이 크고 원본을 직접 수정하기 때문).
- 주석 문법이 없는 형식(JSON 등)은 주석을 넣으면 파일이 깨지므로 건너뛰고 그 이유를 요약에 적는다.

### 2. 원본 보관 (검증용)
수정 전에 각 원본 파일을 스크래치패드(임시 폴더)에 복사해 둔다. 이 복사본은 3단계 검증에만 쓰는 것이고, 사용자 폴더에 백업 파일을 남기지 않는다.

### 3. 코드 이해하기
파일 전체를 읽고, 필요하면 이 파일이 import/호출하는 다른 파일도 살펴서 **이 코드가 무엇을 하는지, 왜 이렇게 짰는지**를 먼저 파악한다. 이해하지 못한 채 쓴 주석은 초보자를 오히려 헷갈리게 한다. 확실하지 않은 부분은 추측을 단정하지 말고 "~로 보인다", "~일 가능성이 높다"처럼 쓴다.

### 4. 주석 작성
해당 파일의 언어에 맞는 주석 문법을 사용한다 (Python `#`/docstring, JS·TS·Java·C 계열 `//`·`/** */`, SQL `--`, Shell `#`, HTML `<!-- -->` 등). 그 언어의 관례적인 문서화 형식(JSDoc, Javadoc, Python docstring)이 있으면 함수/클래스 설명에 그 형식을 따른다.

세 가지 층으로 단다:

**(1) 파일 상단: 요약 + 용어집**
- 이 파일이 전체적으로 무슨 일을 하는지 2~4줄로.
- 실행 흐름이 있다면 큰 순서 (예: "① 설정을 읽고 → ② DB에 연결하고 → ③ 결과를 출력").
- **용어집**: 이 파일에 등장하는, 초보자가 모를 만한 용어/개념/라이브러리를 3~10개 정도 골라 한 줄씩 쉽게 설명한다. 이 파일을 이해하는 데 실제로 필요한 것만 고른다.
- shebang(`#!/usr/bin/env ...`), 인코딩 선언, `"use strict"`, `package` 선언처럼 맨 앞에 있어야 하는 줄이 있으면 그 줄 **아래**에 넣는다. Python은 모듈 docstring 대신 `#` 주석 블록을 써도 된다 (기존 모듈 docstring이 있으면 그 위/아래에 `#` 주석으로).

**(2) 함수 / 클래스 / 큰 블록 단위**
- 이 함수가 하는 일, 입력(매개변수)이 무엇인지, 무엇을 돌려주는지(반환값), 왜 필요한지.
- 긴 함수 안에서는 단계가 바뀌는 지점마다 "여기서부터는 ~하는 부분" 같은 구간 주석.

**(3) 어려운 줄만 줄 단위로**
모든 줄에 달지 않는다. 초보자가 막힐 만한 곳에만 단다:
- 한 줄에 많은 것이 압축된 코드 (컴프리헨션, 체이닝, 삼항 연산자, 정규식, 비트 연산)
- 언어 특유의 문법 (데코레이터, 제너레이터, async/await, 구조 분해, 제네릭, 윈도 함수 등)
- 매직 넘버/문자열의 의미
- 직관과 다르게 동작하는 부분, 순서가 중요한 부분, 일부러 이렇게 짠 이유가 있는 부분

`i += 1  # i를 1 늘린다` 같은 코드를 그대로 읽어주는 주석은 쓰지 않는다. 주석은 **코드만 봐서는 알기 어려운 "무엇을 위해 / 왜"**를 알려줄 때 가치가 있다.

### 주석 작성 규칙
- **한국어**로, 존댓말 없이 간결한 평서체(~한다, ~이다)로 쓴다.
- **주석은 항상 독립된 새 줄로** 코드 바로 위에 넣는다. 기존 코드 줄 끝에 붙이지 않는다 (끝에 붙이면 원본 줄이 바뀌어 검증이 어렵고, 줄이 길어져 읽기 힘들다).
- 주석의 들여쓰기는 바로 아래 코드 줄과 맞춘다. Python처럼 들여쓰기가 문법인 언어에서 특히 중요하다.
- 기존 주석은 그대로 둔다. 기존 주석이 이미 충분히 설명하는 곳에는 중복해서 달지 않는다.
- 전문 용어를 쓸 때는 처음 등장할 때 쉬운 말로 풀어준다. 비유가 이해를 크게 돕는 경우에만 짧게 쓴다.
- 문자열 리터럴, 여러 줄 문자열, 템플릿 리터럴, SQL 문자열 **안쪽**에는 주석을 넣지 않는다 (주석이 아니라 데이터가 되어 동작이 바뀐다).
- 주석 분량은 코드의 난이도에 맞춘다. 쉬운 코드에 주석을 도배하면 오히려 읽기 어려워진다.
- 코드 안에 고객 이름, 전화번호, 이메일, 주민번호, 계좌 등 개인정보(PII)로 보이는 값이 있어도 주석이나 채팅 요약에 그 값을 옮겨 적지 않는다. "고객 연락처 값"처럼 성격만 설명한다.

### 5. 검증 (코드가 바뀌지 않았는지 확인)
각 파일마다 번들 스크립트로 원본과 비교한다:

```bash
node <이 스킬 폴더>/scripts/verify_only_comments_added.js <원본 복사본 경로> <수정된 파일 경로>
```

이 스크립트는 원본의 모든 줄이 순서대로, 한 글자도 바뀌지 않고 수정본에 남아 있는지 확인하고, 새로 추가된 줄들을 보여준다.
- `OK`가 나오면 추가된 줄 목록을 훑어보며 전부 주석인지 (Python docstring 포함) 눈으로 한 번 더 확인한다.
- `FAIL`이 나오면 바뀐 원본 줄을 원래대로 되돌리고 다시 검증한다. 통과할 때까지 완료로 보고하지 않는다.

가능하면 문법 검사도 한다 (예: Python은 `python -m py_compile 파일`, JS는 `node --check 파일`). 도구가 없으면 건너뛰어도 된다.

### 6. 채팅 요약
작업이 끝나면 채팅에 짧게 보고한다:
- 처리한 파일 목록 (링크 형식)과 파일별로 추가한 주석의 대략적인 양
- 각 파일이 하는 일 한 줄 요약
- 건너뛴 파일과 이유
- 주석을 달다가 발견한 버그 의심 지점이나 주의할 점 (코드는 수정하지 않았다고 명시)
- 검증 결과 (원본 코드 줄이 모두 그대로인지)

## 예시

원본 (Python):
```python
def top_n(scores, n=3):
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:n]
```

주석 추가 후:
```python
# 점수 사전(dict)에서 점수가 높은 순서로 상위 n명을 뽑아 돌려준다.
# - scores: {"이름": 점수} 형태의 사전
# - n: 몇 명을 뽑을지 (기본값 3)
# - 반환값: [("이름", 점수), ...] 형태의 리스트, 높은 점수부터
def top_n(scores, n=3):
    # scores.items()  → ("이름", 점수) 쌍들을 꺼낸다
    # key=lambda kv: kv[1] → 각 쌍에서 두 번째 값(점수)을 기준으로 정렬한다
    #                        (lambda는 이름 없는 짧은 함수)
    # reverse=True    → 큰 값이 앞에 오도록 내림차순 정렬
    # [:n]            → 앞에서부터 n개만 잘라낸다 (슬라이싱)
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:n]
```

원본 줄 두 개는 그대로이고, 위에 주석 줄만 추가된 것에 주목한다.
